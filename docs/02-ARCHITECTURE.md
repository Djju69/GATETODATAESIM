# GATETODATA eSIM — Архитектура

## 1. Принципы

- **Один код, один хостинг.** Бэкенд сайта, Telegram-бот и админка — единое приложение. Минимум сервисов = минимум стоимости и точек отказа.
- **Поставщик за интерфейсом.** Весь домен зависит от `EsimProvider`. TELMO — первый адаптер, второй провайдер подключается без изменения магазина.
- **Деньги и выдача — state machine заказа.** eSIM выдаётся только из статуса `PAID`, переходы идемпотентны.
- **Секреты только в env.** В репозиторий не попадают ключи TELMO, Telegram, платёжные ключи.

## 2. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Runtime | Node.js 22 (уже установлен) | Один язык для сайта, бота, интеграций |
| Фреймворк | **Next.js 15 (App Router) + TypeScript** | SSR/SEO каталога, API routes для вебхуков, единый деплой, Mini App = тот же код |
| БД | **SQLite (WAL) через better-sqlite3** | Ноль стоимости, надёжно на одном VPS при наших объёмах; миграции в dеslite-схеме; позже — Postgres при росте (слой запросов изолирован) |
| ORM/доступ | Тонкий репозиторийный слой поверх SQL | Без тяжёлых зависимостей, полный контроль |
| Telegram | **grammY** | Современный, типизированный, inline keyboards, webhook/long-poll |
| Дизайн | Tailwind CSS + собственный дизайн-токен | Быстро, без CSS-перегруза |
| Деплой | Один VPS (например, $4–6/мес) + Caddy (авто-TLS) + PM2/systemd | Дёшево, просто |
| Резервные копии | cron: sqlite `.backup` + выгрузка на внешнее хранилище | Обязательное требование |

Альтернативы отклонены: отдельный Fastify-сервис (удвоение деплоя без нужды), Postgres на старте (лишняя стоимость/сложность), microservices (не оправданы объёмом).

## 4. Ключевые схемы

### 4.1 Поставщик (интерфейс)

```ts
interface EsimProvider {
  id: string;                       // 'telmo'
  listCatalog(): Promise<CatalogItem[]>;   // страны, регионы, глобал, пакеты, себестоимость
  createOrder(req: ProviderOrderRequest): Promise<ProviderOrderResult>; // id, esim (iccid, qr, lpa)
  getOrder(providerOrderId): Promise<ProviderOrderStatus>;
  getBalance?(): Promise<number>;
}
```
- Каталог поставщика синхронизируется в нашу БД (`sync-catalog` по cron/вручную): **витрина читает только нашу БД** — быстрый каталог и независимость от доступности поставщика.
- Себестоимость (wholesale) хранится у нас; розница = правило наценки в админке (глобальный %, мин. наценка, переопределение по стране/пакету).

### 4.2 Заказ — state machine

```
DRAFT ──create──> AWAITING_PAYMENT ──paid──> PAID ──provisioning──> DELIVERED
   │                     │                     │                        
   └──cancel/expire──────┘                     └─provider_error──> PROVIDER_FAILED (retry из админки)
DELIVERED ──> EXPIRED / REFUNDED (админ)
```
- Каждый переход — атомарный UPDATE с условием по текущему статусу (защита от двойного клика/двойного webhook).
- `paid` обрабатывается идемпотентно: повторный webhook того же платежа = no-op.
- Выдача: из `PAID` → `createOrder` у поставщика → сохраняем eSIM-данные → `DELIVERED` → уведомление (сайт-страница + Telegram, если привязан).

### 4.3 Платежи

```ts
interface PaymentProvider {
  id: 'stars' | 'usdt';
  createIntent(order): Promise<{payUrl?|invoicePayload?}>;
  verifyWebhook(req): Promise<{orderId, externalId, amount, currency} | null>;
}
```
- **Stars**: Telegram Bot Payments (provider_token XTR), success_payment → идемпотентный обработчик.
- **USDT**: генерируем адрес+сумму (сеть TRC-20/TON), фоновая сверка поступлений (TronGrid/TON center free API) → подтверждение. Адреса не переиспользуем между заказами (приватность + простая сверка).
- Оба — webhook-подтверждение, eSIM только после `PAID`.

### 4.4 Промокоды

- Наши промокоды в нашей БД: код, тип (% / фикс), значение, период, лимит использований, «один раз на пользователя», «только первый заказ», min-сумма — **зеркало условий кампании TELMO**.
- TELMO-кампания: до подтверждения через API трактуем как наш промокод `TELMO1` с условиями ($1, min $5, первый заказ, лимит 100) — скидка уменьшает нашу розничную цену, себестоимость списывается как обычно. Если TELMO подтвердит применение кампании через API — добавим параметр в адаптер.
- Реферальные коды: отдельная сущность, начисление баланса/скидки — во второй итерации (схема заложена).

### 4.5 Аутентификация

- Покупка **без регистрации**: email или «войти через Telegram» → создаём/находим сессионного пользователя по email / telegram_id.
- Личный кабинет: magic-link на email + Telegram Login (initData) → единый профиль на сайте и в боте (одна таблица users).
- Админка: логин+пароль (хеш), сессионные cookie (HttpOnly, SameSite), RBAC: `admin` / `manager`; журнал действий `audit_log`.

## 5. Сценарии (кратко)

**Сайт:** Главная → поиск страны → страна → тариф → checkout (email/Telegram, промокод) → платёж (Stars/USDT) → `/esim/[token]` (QR, LPA, инструкции iPhone/Android, активация, срок) → письмо+уведомление. Повторный доступ по ссылке из «Мои eSIM».

**Бот:** 🌍 Купить eSIM → страна (поиск кнопками/инлайн) → тарифы (карточки) → детали+промокод → 💳 Оплатить (Stars инвойс / USDT-инвойс) → success → карточка eSIM с QR (фото) + LPA + инструкция. Навигация: «◀️ Назад», «❌ Отмена», заказы/eSIM/поддержка — из главного меню. Защита от двойного платежа: инвойс создаётся один раз на заказ, повторные нажатия отдаются тот же payload.

**Мини App (этап 2):** открывается из бота, использует initData для автологина, общий каталог/корзина/checkout.

## 6. Нефункциональные требования

- **Безопасность:** env-only секреты; проверка подписей webhook (TELMO, Telegram secret token); валидация всех входных данных (zod); rate-limit на API и checkout; CSP; HttpOnly cookies; хеширование паролей (argon2/bcrypt); запрет прямого доступа к БД извне.
- **Идемпотентность:** платёжные и провайдерские webhook-и; повторная выдача eSIM исключена state-машиной + уникальным `provider_order_id`.
- **Валюты:** все суммы — целые минорные единицы (центы USD) в БД; округление при отображении; фиксация курса в заказе.
- **Логи:** pino-логи в файл + stdout, request_id, ошибки провайдера — в таблицу `provider_errors` (видны в админке).
- **Бэкапы:** ежедневный cron `scripts/backup.ts` (sqlite online backup + ротация + оповещение).

## 7. Дизайн-система GATETODATA

- **Концепция:** «signal» — тёмный технологичный travel-tech, акцентный неоновый сигнал связи.
- **Палитра:**
  - Фон: `#0B0F14` (ink), поверхности `#121821`, `#1A2230`
  - Текст: `#F2F5F8` / вторичный `#93A1B1`
  - Акцент: `#00E5A0` (signal green — «связь онлайн»), hover `#00C98C`
  - Второй акцент: `#4D8BFF` (для ссылок/регионов)
  - Ошибки `#FF5C6C`, предупреждения `#FFB454`
- **Шрифты:** Inter (текст) + Space Grotesk (заголовки/цифры) — локальные/Google fonts, font-display swap.
- **Компоненты:** карточка тарифа (страна, флаг, данные, срок, цена, кнопка), чип-фильтры, поиск с автокомплитом по странам, статус-чипы заказов, QR-блок, step-indicator checkout.
- **Мобильность-first:** все сценарии проектируются от 360px; тап-таргеты ≥44px; sticky CTA на странице тарифа.
- **Производительность:** SSR каталога, кэш каталога в памяти/БД, оптимизация изображений (флаги — SVG/emoji), без тяжёлых библиотек.
